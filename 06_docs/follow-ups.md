### D-1 — a zone-only alert in an area you do not track, when a radius is set

**What ships today.** `app/severe.go:scopeEvents` keeps a point-less alert when
the app is separately tracking the same alert on a location in scope, tied by
normalised alert id. "In scope" is the radius as well: `severeDeck.AlertKeysWithin`
builds the tie set from tracked locations inside it, because the RECENT table is
seeded with the fifty largest US cities and each fetches its own alerts — an
unscoped tie would hand the marquee and the spoken read to a warning a thousand
miles away. That covers every hazard for a place the listener has told the app
they care about, on every surface — window, tape, takeover and the spoken read.

The tie also refuses any id `severe.NormalizeID` does not accept as a CAP alert.
An empty key would otherwise match every point-less event that also lacked an
id, so one unidentifiable tracked alert would pull the national feed's whole
zone-only output past the radius.

**Three claims made while getting here were wrong**, corrected so the next
reader does not inherit them from `400b847`'s or `e26661f`'s messages:

- *"scopeEvents refuses to tie an event with no id"*, describing a dedicated
  branch for the empty id. That branch was inert — `NormalizeID("")` already
  returns not-ok — and it has been deleted rather than left to read as the guard
  that does the work. The guard is `NormalizeID`'s own rejection.

- *"The severe window was never broken."* It was degraded. The row reached the
  window through the location's own zone query, so the listener saw the warning
  — but without the national CAP feed's half it lost that half's detail.
- *"The tape, the takeover and the spoken alert are fed from the feed alone."*
  They are not. `tickerDeck.tapeItems` appends `laneItems(severe.LaneRows())`,
  which is how Advisories and Special Weather Statements — the two lanes the
  national feed cannot fill — reach the marquee at all.

**What it does not cover.** A zone-only alert for an area with no tracked
location. Such an alert carries no coordinates, and zones only enter the app via
tracked locations, so there is nothing to measure and nothing to match. With
ALERTS-EVENTS set to a radius it is excluded; with "All" it is shown.

**Why a UGC tie does not close it.** `domains/weather/nws/alerts.go` already
decodes `affectedZones` and already matches feed alerts to tracked locations by
zone over the full untruncated list; its output *is* `locs[].Alerts`, which is
what the id tie keys on. Carrying UGC onto `globalfeed.Event` would reach the
same answer by a longer route. This was proposed and withdrawn — recorded so it
is not proposed again.

**The two real options.**

1. **Resolve the alert's zones to geometry.** NWS serves zone polygons; cache
   them and measure the distance from the default location. Exact, and the only
   thing that truly answers "is this county within N miles". It is a new fetch,
   a new cache with its own bound and TTL, and a new failure mode when a zone
   lookup fails — closer in size to adding a provider than to a patch. Needs its
   own DISCOVER and its own scoped red team.
2. **Never drop a point-less alert when a radius is set.** One line, and safe in
   the direction that matters. It makes a filtered setup noisier by every
   zone-only product nationwide.

**What decides it: a measurement, not an estimate.** How many zone-only alerts
would a filtered setup actually gain under option 2 on a normal day and on an
outbreak day? Take it from the live national feed before choosing. Option 2 is
only unacceptable if that number is large, and nobody has counted it.

**Posture.** Shipping today's behaviour as the final answer is not on the table
(see the release-posture calibration): the listener is told about hazards where
they live, but a filtered setup is silent about a county next door.
